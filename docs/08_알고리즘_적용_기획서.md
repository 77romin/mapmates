# 알고리즘 적용 기획서

적용한 알고리즘은 세 가지다. 소스는 `back/src/main/java/com/ssafy/mapmates/algorithm`에 있다.

---

## 알고리즘 적용 기획서 #1

- **내용**: 비트마스크 DP와 2-opt를 이용한 여행 동선 최적화 서비스
- **적용 알고리즘**: Held-Karp(비트마스크 동적계획법), 최근접 이웃(Greedy) + 2-opt 지역 탐색

### 알고리즘 개요

하루에 방문할 장소들을 한 번씩 모두 들르면서 총 이동 거리를 최소로 만드는 문제는 외판원 문제(TSP)다. 모든 순서를 다 해 보면 O(n!)이라 10곳만 넘어도 계산할 수 없다.

- **Held-Karp**: `dp[mask][i]`를 "출발지에서 시작해 mask에 포함된 장소를 모두 방문하고 i에서 끝나는 최소 거리"로 정의한다. 부분 문제의 최적해를 재사용해 시간 O(n²·2ⁿ), 공간 O(n·2ⁿ)으로 **최적해**를 구한다.
- **최근접 이웃 + 2-opt**: 현재 위치에서 가장 가까운 미방문 장소를 계속 고르는 Greedy로 초기 경로를 만들고(O(n²)), 경로의 두 간선을 골라 그 사이 구간을 뒤집었을 때 짧아지면 적용하는 과정을 더 줄어들지 않을 때까지 반복한다. 최적해는 보장하지 않지만 빠르게 좋은 근사해를 얻는다.

### 적용 서비스

플랜 보드의 **동선 최적화** 버튼, AI 길잡이의 **OPTIMIZE_ROUTE Tool**

### 적용 서비스 개발 개요

플랜 보드에서 사용자가 담은 순서대로 방문지가 쌓이면 동선이 지그재그가 되기 쉽다. "동선 최적화"를 누르면 현재 일차의 방문지 번호를 서버(`POST /api/plans/optimize`)로 보내고, 서버는 각 방문지의 위경도로 Haversine 거리 행렬을 만든다.

입력 규모에 따라 알고리즘을 나눴다. n=12일 때 Held-Karp의 연산량은 12²×2¹² ≈ 59만으로 즉시 끝나지만, n=20이면 약 4억으로 급증하고 메모리도 n·2ⁿ개의 double이 필요하다. 하루 일정은 대부분 10곳 이하이므로 **12곳 이하는 Held-Karp로 최적해**를, **그보다 많으면 최근접 이웃 + 2-opt로 근사해**를 구한다. 첫 번째 방문지는 출발지(숙소 등)로 고정하고, 여행 동선은 원점으로 돌아올 필요가 없으므로 복귀 간선은 제외했다.

응답에는 사용한 방법, 최적화 전후 거리, 새 순서를 담는다. 화면은 순서를 재배치하고 "87.4km → 68.9km (18.5km 단축)"처럼 결과를 보여준다. 부산 관광지 8곳으로 실행한 결과 87.4km가 68.9km로 줄었다(Held-Karp 사용).

| 구분 | Held-Karp | 최근접 이웃 + 2-opt |
|---|---|---|
| 적용 조건 | n ≤ 12 | n > 12 |
| 해의 품질 | 최적 | 근사 |
| 시간 복잡도 | O(n²·2ⁿ) | O(n²) × 개선 반복 횟수 |
| 공간 복잡도 | O(n·2ⁿ) | O(n²) (거리 행렬) |

## 알고리즘 적용 기획서 #2

- **내용**: 코사인 유사도를 이용한 메이트 추천 서비스
- **적용 알고리즘**: 코사인 유사도(Cosine Similarity) + 정렬

### 알고리즘 개요

코사인 유사도는 두 벡터가 이루는 각도의 코사인 값으로 방향이 얼마나 비슷한지를 0~1로 나타낸다. 여행 취향 태그를 "있다/없다"의 0·1 벡터로 보면 내적은 공통 태그 수, 벡터의 크기는 태그 수의 제곱근이 되어 `cos = |A∩B| / (√|A| × √|B|)`로 계산된다. 태그를 많이 단 쪽이 유리해지지 않도록 크기로 정규화된다는 점이 단순 공통 개수 비교보다 낫다.

### 적용 서비스

메이트 찾기 화면의 **취향 일치 %** 표시와 **추천 순 정렬**

### 적용 서비스 개발 개요

회원은 가입·마이페이지에서, 모집자는 모집글에서 여행 스타일 태그(바다, 등산, 맛집, 사진, 역사, 도시, 휴양)를 최대 3개 고른다. 모집글 목록을 요청하면 서버(`MateService.list`)는 로그인 회원의 태그를 HashSet으로 만들고, 각 모집글의 태그 집합과 교집합 크기를 세어 유사도를 계산한다. 집합 조회가 O(1)이므로 글 하나당 O(|A|+|B|), 전체는 O(m·k)(m: 모집글 수, k: 태그 수)다.

계산한 값은 0~100의 `matchRate`로 응답에 담고, "모집 중 우선 → 일치도 내림차순"으로 정렬한다(O(m log m)). 화면에는 "♥ 취향 일치 82%"로 표시된다. 태그가 `바다,맛집,사진`인 회원에게 `맛집,바다` 모집글은 2/(√3·√2) ≈ 82%, `등산,맛집,역사` 모집글은 1/(√3·√3) ≈ 33%로 계산된다.

## 알고리즘 적용 기획서 #3

- **내용**: 기하 중앙값을 이용한 메이트 중간 집결지 추천 서비스
- **적용 알고리즘**: Weiszfeld 반복법(기하 중앙값) + 범위 필터링 후 거리 정렬

### 알고리즘 개요

여러 지점으로부터의 **거리 합**이 최소가 되는 점을 기하 중앙값이라고 한다. 좌표 평균(무게중심)은 거리 제곱의 합을 최소화하므로 멀리 사는 한 명에게 크게 끌려가지만, 기하 중앙값은 그런 치우침이 덜하다. 닫힌 해가 없어서 Weiszfeld 반복법으로 구한다. 현재 추정점에서 각 지점까지의 거리의 역수를 가중치로 한 가중 평균을 새 추정점으로 삼는 과정을 수렴할 때까지 반복한다. 1회 반복은 O(n)이다.

### 적용 서비스

플랜 보드의 **중간 집결지 찾기**

### 적용 서비스 개발 개요

메이트들은 마이페이지에서 지도를 클릭해 출발지를 등록한다. 플랜 보드에서 "중간 집결지 찾기"를 누르면 서버(`GET /api/plans/{id}/meeting-point`)가 참여자들의 출발지 좌표를 모아 평균점에서 시작해 최대 100회 반복하며, 좌표 변화가 10⁻⁷도 미만이면 멈춘다. 거리는 Haversine으로 계산하고, 추정점이 어떤 출발지와 겹쳐 0으로 나누는 것을 막기 위해 거리 하한을 둔다.

집결지 좌표만으로는 만날 장소를 정하기 어려우므로 주변 5km의 관광지·문화시설·음식점 5곳을 함께 추천한다. 이때 5만 건 전체에 거리 계산을 하지 않도록, 반경을 위경도 사각형 범위로 바꿔 좌표 인덱스로 후보를 먼저 줄이고(필터), 남은 후보만 정확한 거리를 계산해 정렬한다(정제). 같은 방식을 관광지 상세의 주변 축제·상권 조회에도 사용한다.

## 자료구조·알고리즘 선택 요약

| 문제 | 선택 | 이유 |
|---|---|---|
| 방문 순서 최적화 | 비트마스크 DP / 2-opt | 입력 규모(12곳 기준)에 따라 정확도와 시간을 맞바꿈 |
| 취향 비교 | HashSet + 코사인 유사도 | 태그 포함 여부를 O(1)에 확인, 태그 수에 대한 정규화 |
| 집결지 | Weiszfeld 반복법 | 거리 합 최소화, 한쪽으로 치우치지 않음 |
| 주변 검색 | B-Tree 인덱스 범위 조회 + 정렬 | 전체 탐색 O(N) 대신 후보만 계산 |
| 외부 API 캐시 | ConcurrentHashMap | 동시 요청에서 안전한 O(1) 조회, 만료 시각과 함께 보관 |
