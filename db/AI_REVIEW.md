# 스키마 검증·개선 기록

최초 검증은 `verify/README.md` 및 두 결과 파일을 따른다. 관광지 50,915행, 초기 26개 시나리오와 팀원의 프론트 대조 검증을 보존했다. 최종 DDL은 `schema.sql`, 초기 적재 후 정리는 `init/03-clean.sql`, 시연 데이터는 `seed.sql`이다.

| 검토 사항 | 반영 |
|---|---|
| 시도별 반복 구군 코드 | 복합 FK로 다른 시도의 구군 참조 차단 |
| TourAPI 39번 | 음식점으로 정정 |
| 누락 관광지와 일정/찜 | 없는 관광지만 먼저 등록, 기존 공공 데이터 보존 |
| 잘못된 좌표 94행 | NULL 처리, 주변 조회에서 제외 |
| 계획·참가자 중복 | 계획당 동행 UNIQUE, 참가자·찜 복합 PK |
| 불필요한 모집자 중복 | 계획 소유자에서 유도 |
| 댓글 대상 무결성 | 게시글/동행 XOR CHECK, 답글 대상 일치 Service 검사 |
| 조회수와 수정 시각 | 팀원 f778489 통합, 수정 SQL에서만 updated_at 기록 |
| 동시 참가 | 실제 HTTP 병렬 요청으로 검증, 계획 행 잠금+READ COMMITTED |
| 성능 | 지역/콘텐츠, 좌표, 소유자, 게시판/작성일, 댓글 대상 인덱스 |

좌표 B-tree와 SPATIAL 인덱스의 기존 비교는 보존하되, 최종 서비스는 NULL 좌표를 허용하는 B-tree 범위 조회 후 구면 거리 조건을 사용한다. 기존 비교의 읽는 행 수는 옵티마이저 추정치이며 서비스 성능을 보장하는 수치로 해석하지 않는다.

인기 장소는 회원 수 `COUNT(DISTINCT owner_id)`와 계획 수 `COUNT(DISTINCT plan_id)`를 각각 집계하여 같은 계획에 반복 추가한 장소가 중복 집계되지 않게 한다. 관광지 ID로 묶으며 이름·좌표가 우연히 같은 서로 다른 ID는 별도 장소로 취급한다. 동률은 회원 수, 계획 수, DB의 한국어 문자열 정렬 결과, ID 순서다.
